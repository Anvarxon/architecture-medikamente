# Задание 5. Cutover-план миграции

## 1. Обоснование выбора стратегии

### 1.1. Сравнение вариантов

| Критерий | High-level design | Parallel run | Branch by abstraction |
|---|---|---|---|
| Суть | Проектирование новой системы «с нуля» по доменным границам и переключение целиком | Старая и новая системы работают одновременно, нагрузка переводится постепенно | Функциональность переносится слой за слоем за абстракцией внутри одной системы |
| Риск для непрерывности работы клиники | Высокий: переключение «одним днём», откат дорогой | Низкий: старый контур остаётся рабочим, можно вернуться в любой момент | Средний: зависит от зрелости кода, требует наличия кодовой базы |
| Применимость к «Медикаменте» | Нужна как основа архитектуры, но как способ перехода не подходит | Подходит: критичные процессы (запись, оплата) нельзя останавливать | Ограниченно: мигрируем не монолитный код, а Excel, файлы и коробочную 1С — абстракцию вводить в них негде |
| Стоимость | Средняя | Высокая: два контура работают одновременно, нужна синхронизация | Низкая, но требует зрелых инженерных практик |
| Проверяемость результата | Низкая: сравнение только после переключения | Высокая: можно сверять результаты двух систем на одних и тех же данных | Средняя |
| Главный риск | «Большой взрыв» и откат | Рассинхронизация данных между контурами | Долгое сосуществование версий и рост сложности |

### 1.2. Выбранная стратегия

**Основная стратегия — Parallel run** (параллельная работа старого и нового контуров с поэтапным
переводом нагрузки), **дополненная элементами Branch by abstraction** на интеграционном уровне.

Почему Parallel run:

1. **Медицинская организация не может остановиться.** Запись пациентов, приём и касса работают
   ежедневно; «большой взрыв» с откатом на сутки означает сорванные приёмы, потерю выручки
   и репутационный ущерб — то, чего компания как раз стремится избежать.
2. **Данные требуют верификации.** Исходные данные лежат в Excel и сканах, качество низкое, есть дубли.
   Только параллельная работа позволяет сверять результат новой системы со старой на одних и тех же
   данных и находить расхождения до отказа от старого контура.
3. **Персонал нужно переучить.** 20 административных и 15 медицинских сотрудников переходят
   с Excel на портал. Параллельный период даёт время на обучение без риска остановки процесса.
4. **Регуляторные ограничения.** Переключение ККМ и обменов с 1С затрагивает 54-ФЗ и 402-ФЗ:
   нужна возможность вернуться на прежний канал в течение минут.

Где применяется Branch by abstraction: для интеграций, которые нельзя дублировать (ККМ, обмены с 1С,
лаборатория), вводится слой абстракции — адаптер интеграции с переключателем реализации
(`feature flag`: «старый OLE-канал» / «новый шлюз»). Это позволяет переключать конкретную интеграцию
независимо от остальной системы и мгновенно возвращаться назад.

Ограничения выбранной стратегии, которые нужно контролировать:

- удвоенная нагрузка на инфраструктуру и на персонал в переходный период;
- необходимость односторонней синхронизации данных и регулярных сверок;
- риск «вечного parallel run» — поэтому в плане зафиксированы жёсткие критерии выхода и дата
  отключения старого контура.

### 1.3. Принципы перехода

- **Одно направление записи в каждый момент времени.** В каждой фазе определена система-владелец
  записи (system of record); вторая система получает данные только на чтение или через синхронизацию.
- **Волны по филиалам и по процессам.** Сначала пилотная группа (2 сотрудника ресепшена, 3 врача),
  затем весь головной офис, затем филиалы.
- **Каждая фаза имеет критерии входа, критерии успеха и точку принятия решения** (go / no-go).
- **Откат возможен на любой фазе** и отрепетирован до начала.

## 2. Cutover-план

Роли: **CTO** — технический директор (архитектор, руководитель миграции); **PM** — руководитель проекта;
**DevOps** — инженер эксплуатации; **DBA** — администратор БД и данных; **DE** — дата-инженер;
**DPO** — офицер ИБ и ответственный за ПДн; **DEV** — команда разработки; **QA** — тестирование;
**BA** — бизнес-аналитик; **OPS** — руководители подразделений (ресепшен, касса, бухгалтерия, склад);
**NET** — администратор сети; **Vendor** — подрядчик (1С, лаборатория, провайдеры).

## 3. Мониторинг перехода

Мониторинг — отдельный контур, который работает с первого дня параллельной работы и является
источником данных для решений go / no-go и отката.

### 3.1. Что отслеживается

| Категория | Показатель | Целевое значение | Источник | Кто смотрит | Реакция при отклонении |
|---|---|---|---|---|---|
| Доступность | Uptime сервиса записи и портала | ≥ 99,5 % в рабочие часы | Blackbox-проба, VictoriaMetrics | DevOps (дежурный) | Алерт → перевод пользователей на старый контур |
| Производительность | Время отклика API, 95-й перцентиль | ≤ 500 мс | OpenTelemetry, Grafana | DevOps | Ограничение фоновых миграций, масштабирование |
| Производительность | Время отклика PDP и PII Vault | ≤ 30 мс | Метрики сервисов | DEV | Кеширование решений, оптимизация запросов |
| Целостность данных | Расхождение числа записей старый / новый контур | 0 | Ежедневный сверочный отчёт | DE, BA | Остановка перевода волн, разбор расхождения |
| Целостность данных | Расхождение сумм выручки за смену | 0 | Сверка Billing и 1С | Бухгалтерия, BA | Разбор до закрытия смены |
| Миграция | Доля успешно перенесённых карт, доля спорных | ≥ 99,9 % / ≤ 1 % | Отчёт загрузчика | DBA | Повторный прогон партии |
| Безопасность | Аномальный доступ: массовое чтение, доступ вне часов, доступ к «чужому» пациенту | 0 срабатываний | WORM-журнал → SIEM | DPO | Инцидент, блокировка сессии |
| Безопасность | Срабатывания DLP на исходящих каналах | 0 подтверждённых | DLP | DPO | Разбор с сотрудником, при подтверждении — инцидент |
| Качество данных в озере | Доля полей с проставленным классом | 100 % | Движок классификации | DE | Карантин набора данных |
| Бизнес-процесс | Доля записей, созданных в новом контуре | Растёт по плану волн | Дашборд перехода | PM, OPS | Разбор причин с подразделением |
| Поддержка | Число обращений в поддержку по новой системе | Снижается неделя к неделе | Служба поддержки | PM | Точечное дообучение, доработка UX |
| Инфраструктура | Загрузка CPU, памяти, IOPS, глубина очередей Kafka | ≤ 70 % от ёмкости | VictoriaMetrics | DevOps | Масштабирование до следующей волны |

### 3.2. Как организован мониторинг

- **Единый дашборд перехода** в Grafana: доступность, задержки, расхождения сверок, доля нагрузки
  в новом контуре, открытые инциденты. Один экран, по которому принимается решение на ежедневном статусе.
- **Ежедневный сверочный отчёт** формируется автоматически в 8:00 и рассылается CTO, PM, руководителям
  ресепшена и кассы; расхождение любого размера — повод для разбора до начала приёма.
- **Алертинг**: критические алерты (недоступность, сбой фискализации, инцидент ИБ) — дежурному
  и CTO немедленно; предупреждения — в рабочий чат проекта.
- **Гиперкейр** после каждой волны: две недели усиленного наблюдения, ежедневная 15-минутная встреча
  команды перехода с разбором инцидентов.
- **Пострелизный отчёт** по каждой фазе: выполнены ли критерии выхода, какие дефекты открыты,
  решение о переходе к следующей фазе.

### 3.3. Критические моменты (точки невозврата)

| Момент | Почему критичен | Как страхуемся |
|---|---|---|
| Перевод 1С в клиент-серверный режим (этап 1.3) | Затрагивает бухгалтерию и складской учёт целиком | Полная резервная копия, работы в закрытый период, проверенный откат на файловый режим |
| Первое переключение фискализации (этап 3.2) | Остановка кассы = остановка приёма оплаты, 54-ФЗ | Пилот на одной кассе, feature flag на старый канал, дежурство подрядчика |
| Отказ от двойного учёта в Excel (этап 3.3) | Исчезает «второе мнение» о выручке | 10 рабочих дней сверок без расхождений до отключения |
| Перевод ЭМК (этап 3.5) | Врач не должен потерять доступ к истории пациента | Архив старых файлов в режиме чтения прямо из интерфейса ЭМК |
| Заморозка старого контура (этап 5.1) | После заморозки откат становится дорогим | Аудит доступа к файлам за предыдущий месяц, опрос подразделений, месяц «только чтение» до отключения |
| Удаление старых данных (этап 5.3) | Необратимо | Удаление только после подтверждения владельцами данных и создания архива |

## 4. Управление рисками

### 4.1. Ключевые риски выбранной стратегии

| № | Риск | Вероятность | Влияние | Триггер обнаружения | Меры снижения | Владелец |
|---|---|---|---|---|---|---|
| P-1 | Рассинхронизация данных между контурами | Высокая | Критическое | Ежедневный сверочный отчёт показывает расхождение | Одно направление записи, автоматическая синхронизация, сверки, запрет ручного ввода в старом контуре по мигрированным сущностям | DE |
| P-2 | Двойное бронирование слота | Средняя | Высокое | Жалоба пациента, отчёт по коллизиям | Единый календарь как источник истины, транзакционная блокировка слота, запрет параллельной записи в Excel | DEV |
| P-3 | Остановка кассы при переключении фискализации | Средняя | Критическое | Ошибки фискализации, очередь на кассе | Feature flag и резервный OLE-канал, пилот на одной кассе, дежурство подрядчика, переключение вне пика | DevOps |
| P-4 | Утрата или искажение медицинской истории при миграции | Средняя | Критическое | Расхождение контрольных сумм, выборочная проверка | Миграция на копии, контрольные суммы, ручная верификация спорных карт, доступ к архиву в режиме чтения | DBA |
| P-5 | Слияние карт разных пациентов (ошибка MDM) | Средняя | Критическое | Проверка медперсоналом, обращение пациента | Автоматическое слияние только при полном совпадении набора признаков, остальное — ручное подтверждение | BA |
| P-6 | Перегрузка инфраструктуры двумя контурами | Средняя | Высокое | Метрики CPU, задержки, очереди | Запас ёмкости ×2, нагрузочное тестирование, автоскейлинг, ограничение фоновых миграций окнами | DevOps |
| P-7 | Утечка данных в переходный период (расширенная поверхность) | Средняя | Критическое | SIEM-алерты, DLP | Пентест до запуска, DLP, WORM-аудит, минимизация прав, обучение персонала | DPO |
| P-8 | Сотрудники продолжают вести теневые Excel | Высокая | Среднее | Аудит доступа к файлам, опрос подразделений | Перевод файлов в read-only по графику, обучение, вовлечение руководителей подразделений | OPS |
| P-9 | «Вечный parallel run» | Средняя | Высокое | Срыв критериев выхода из фазы | Жёсткие критерии выхода, дата отключения старого контура в приказе, еженедельный статус у CTO | PM |
| P-10 | Контрагент (лаборатория, 1С) не готов в срок | Высокая | Среднее | Статус по интеграции | Промежуточный защищённый файловый обмен, буфер по срокам, штрафные условия в договоре | CTO |
| P-11 | Потеря ключей шифрования | Низкая | Критическое | Ошибки расшифровки | Резервирование ключей в HSM, процедура восстановления, разделение секрета между двумя ответственными | DPO |
| P-12 | Ошибки в расчёте зарплаты после перевода HR | Средняя | Высокое | Расхождение с расчётом в 1С | Параллельный расчёт один-два периода, сверка до выплаты | Бухгалтерия, DEV |

### 4.2. План действий при возникновении проблем

| Ситуация | Немедленные действия | Кто принимает решение | Порог отката |
|---|---|---|---|
| Расхождение данных между контурами | Остановить перевод новых пользователей, зафиксировать расхождение, восстановить из сверочного отчёта | CTO | Расхождение > 0,5 % записей за день или любое расхождение по платежам |
| Недоступность нового контура | Перевести пользователей на старый контур (он остаётся рабочим), включить резервный канал интеграций | Дежурный DevOps, эскалация CTO | Недоступность > 15 минут в рабочее время |
| Сбой фискализации | Переключить feature flag на старый OLE-канал, продолжить приём оплаты | Дежурный DevOps + старший кассир | Любой сбой длительностью > 5 минут |
| Инцидент безопасности (подозрение на утечку) | Заблокировать учётную запись и сессии, изолировать сервис, снять журналы, уведомить DPO | DPO | Немедленно, без порога |
| Деградация производительности | Включить ограничение фоновых процессов миграции, масштабировать сервис, при необходимости — вернуть часть пользователей на старый контур | DevOps | Время отклика 95-го перцентиля > 1 с в течение 30 минут |
| Ошибка миграции данных | Остановить загрузку, откатить партию по идентификатору партии, перезапустить после исправления | DBA | Любая ошибка целостности |

### 4.3. План отката

Откат возможен на каждой фазе, поскольку старый контур сохраняется рабочим до фазы 5.

| Фаза | Что откатываем | Как | Время отката (цель) | Потери данных |
|---|---|---|---|---|
| 1 | Развёртывание MVP | Пользователи не переведены, откат не затрагивает работу клиники | — | Нет |
| 2 | Пилот | Вернуть пилотных сотрудников в Excel, выгрузить созданные записи в старый формат | ≤ 2 часа | Нет: односторонняя синхронизация обеспечивает наличие данных в обоих контурах |
| 3 | Головной офис | Вернуть волну сотрудников на старый контур; для кассы — переключить feature flag на OLE | ≤ 4 часа, касса ≤ 5 минут | Нет |
| 3.4 | Обмен с 1С | Включить прежний OLE-обмен, повторно провести документы за период | ≤ 4 часа | Нет: обмены идемпотентны |
| 4 | Интеграция с лабораторией | Вернуться к защищённому файловому обмену с псевдонимами | ≤ 1 час | Нет |
| 5 | Отключение старого контура | Восстановление из архива (только чтение), возврат шар в режим записи | ≤ 8 часов | Данные, введённые в новом контуре после заморозки, переносятся вручную |

Обязательные условия готовности к откату: актуальная резервная копия перед каждым переключением,
отрепетированная процедура на stage, назначенный дежурный на время cutover, канал связи
(общий чат и конференция) и заранее подготовленное уведомление сотрудникам.

## 5. Распределение ролей (RACI)

R — исполняет, A — отвечает за результат, C — консультирует, I — информируется.

| Задача | CTO | PM | DevOps | DBA/DE | DPO | DEV | QA | OPS | Vendor |
|---|---|---|---|---|---|---|---|---|---|
| Архитектурные решения и границы сервисов | A/R | C | C | C | C | R | I | I | C |
| План миграции и график | C | A/R | C | C | C | I | I | C | I |
| Инфраструктура и сеть | C | I | A/R | C | C | I | I | I | C |
| Миграция и качество данных | C | I | C | A/R | C | C | C | C | I |
| Правовая база, согласия, уведомление РКН | C | I | I | C | A/R | I | I | I | I |
| Политики доступа (PDP) и аудит | C | I | C | C | A/R | R | C | C | I |
| Разработка сервисов | C | C | C | C | C | A/R | C | C | I |
| Тестирование, нагрузка, пентест | C | C | C | C | C | C | A/R | I | C |
| Обучение и приёмка процессов | I | C | I | I | C | I | C | A/R | I |
| Переключение (cutover) | A | R | R | R | C | C | C | C | C |
| Решение об откате | A/R | C | R | C | C | I | I | C | I |
| Вывод старого контура из эксплуатации | A | R | R | R | C | I | I | C | I |

**Состав дежурной смены на день переключения:** CTO (принятие решений), PM (координация),
DevOps (техническое переключение и мониторинг), DBA (данные и сверки), DPO (контроль доступа
и инцидентов), по одному представителю от ресепшена и кассы, представитель подрядчика 1С на связи.

## 6. Сводная блок-схема переключения (день Х)

```
T-7 дней   Заморозка изменений в новом контуре, финальное регрессионное тестирование
T-3 дня    Репетиция переключения на stage, проверка процедуры отката
T-1 день   Полная резервная копия, уведомление сотрудников, сбор дежурной смены
T-2 часа   Проверка готовности: инфраструктура, мониторинг, каналы связи        ── no-go ──> перенос
T=0        Переключение маршрутизации пользователей на новый контур (волна)
T+15 мин   Смоук-тесты: вход, создание записи, оплата, фискализация, уведомление ── провал ──> откат
T+1 час    Первая сверка данных, проверка метрик и алертов                       ── расхождение ──> откат
T+4 часа   Решение о продолжении или откате (go / no-go)
T+1 день   Полная сверка за сутки, отчёт по инцидентам
T+5 дней   Критерии выхода из фазы выполнены → перевод следующей волны
```
