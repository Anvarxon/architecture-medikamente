## 1. Анализ ситуации

### 1.1. Что мигрирует

| Компонент AS-IS | Целевое состояние | Характер миграции |
|---|---|---|
| Excel-журналы записи, Patients.xlsx, журналы врачей | Appointment Service + PostgreSQL | Перенос данных с очисткой и дедупликацией, смена процесса работы ресепшена |
| Медкарты в файлах и сканах на общем диске | EMR + Document Service + S3 | Перенос файлов, распознавание и привязка к пациенту, смена процесса приёма |
| Payments.xlsx и двойной учёт | Billing + PostgreSQL, единый источник истины | Отказ от параллельного учёта, сверка остатков |
| 1С:Бухгалтерия и 1С:Торговля в файловом режиме | Клиент-серверный режим + обмен через шину | Смена режима работы СУБД, переработка интеграций |
| ККМ через OLE | Защищённый шлюз фискализации | Критично: касса не должна останавливаться (54-ФЗ) |
| Файловый обмен с лабораторией | API-интеграция с псевдонимами | Зависимость от готовности контрагента |
| Файловый сервер, AD, Exchange на одном физическом сервере | Кластер Kubernetes, объектное хранилище, резервная площадка | Замена инфраструктуры |
| Отсутствие ИБ-контуров | IAM, PDP, PII Vault, Consent, Audit, DLP | Новая функциональность, которой раньше не было |

### 1.2. Ключевые процессы, затрагиваемые миграцией

Запись пациента (нельзя останавливать даже на час), приём и ведение медкарты, приём оплаты
и фискализация, лабораторные исследования, учёт ТМЦ, расчёт зарплаты. Первые три критичны:
их остановка означает остановку клиники и прямые финансовые потери.

### 1.3. Формулировка проблемы (голова диаграммы)

> Деградация производительности, доступности и защищённости данных после перехода на новую платформу.

Проблема сформулирована как измеримое следствие, чтобы для каждой причины можно было предложить
проверяемую меру: целевые показатели — доступность сервиса записи не ниже 99,5 %, время отклика
API 95-го перцентиля не более 500 мс при пятикратном объёме, ноль инцидентов утраты медицинских данных.

## 2. Категории причин и выявленные проблемы

Диаграмма Исикавы построена по восьми категориям. Ниже — те же причины с оценкой влияния
и предлагаемыми мерами. Приоритеты: **P1** — устранить до начала миграции, **P2** — в ходе подготовки
и пилота, **P3** — в течение переходного периода.

### 2.1. Инфраструктура

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| Единственный физический сервер в здании офиса, нет резервной площадки | Отказ = остановка клиники, потеря данных | Кластер из трёх узлов, резервная площадка (второй ЦОД или облако в РФ), offsite-копии | P1 |
| Мощностей не хватает на Kubernetes, ClickHouse, Kafka и параллельную работу двух контуров | Деградация обоих контуров одновременно | Расчёт ёмкости с запасом ×2 к пиковой нагрузке, поэтапная закупка до старта parallel run | P1 |
| Каналы связи филиалов не рассчитаны на API-трафик и репликацию | Таймауты, рассинхронизация филиалов | Резервирование каналов, QoS, асинхронная репликация, локальное кеширование справочников | P2 |
| Нет резервного питания, охлаждения и мониторинга «железа» | Незапланированные простои | ИБП, контроль микроклимата, мониторинг оборудования в VictoriaMetrics | P2 |
| Локальные диски: рост объёма ×5 упирается в IOPS | Замедление БД и загрузок в озеро | Объектное хранилище + SSD-массив, разделение горячих и холодных данных | P3 |

### 2.2. Программное обеспечение и архитектура

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| 1С в файловом режиме не выдерживает конкурентный доступ | Блокировки, потеря транзакций при росте нагрузки | Перевод в клиент-серверный режим до начала миграции остальных контуров | P1 |
| Риск «распределённого монолита»: неверные границы сервисов | Цепочки синхронных вызовов, лавинообразные отказы | Проектирование по DDD, event storming, ограничение синхронных вызовов, асинхронность через Kafka | P1 |
| Нет идемпотентности и ретраев | Дубли записей на приём и дубли платежей при переключении | Идемпотентные ключи в API, exactly-once обработка событий, дедупликация | P2 |
| Синхронные вызовы PII Vault и PDP на горячем пути | Рост задержки на каждый запрос | Кеширование решений PDP с коротким TTL, батч-раскрытие токенов, целевой бюджет задержки ≤ 30 мс | P2 |
| Разные версии контрактов у старого и нового контура | Ошибки обмена в период параллельной работы | Версионирование API, обратная совместимость, contract testing | P3 |

### 2.3. Данные и миграция

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| Excel и сканы без схемы, низкое качество, дубли пациентов | Некорректная история лечения, ошибки в записи | Профилирование и очистка данных, правила дедупликации, ручная верификация спорных случаев медперсоналом | P1 |
| Нет уникального идентификатора пациента | Слияние карт разных людей или потеря истории | Построение мастер-записи пациента (MDM) по совокупности признаков, ручное подтверждение спорных пар | P1 |
| Недооценка объёма исторических данных и сканов | Окно миграции не укладывается в регламент | Инвентаризация объёма, пробная миграция на копии, перенос архива фоном после cutover | P1 |
| Дрейф структуры источников | Ломается загрузка и классификация | Schema Registry + Drift Detector (Task6), schema-on-read, карантин для изменившихся структур | P2 |
| Обратная синхронизация при parallel run | Конфликты и расхождение остатков | Одно направление записи в каждый момент, сверочные отчёты, чёткое правило разрешения конфликтов | P2 |

### 2.4. Интеграции

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| ККМ через OLE: замена канала рискует остановить кассу | Невозможность принимать оплату, нарушение 54-ФЗ | Пилот на одной кассе, сохранение старого канала как резервного, переключение вне часов пик | P1 |
| Лаборатория не готова к API | Файловый обмен остаётся узким местом и каналом утечки | Промежуточный вариант: шифрованный файловый обмен с псевдонимами по SFTP, параллельно — разработка API | P2 |
| 1С требует перевода в клиент-серверный режим и переработки обменов | Простой бухгалтерии, ошибки в проводках | Отдельный подпроект с бухгалтерией, миграция в закрытый период (после сдачи отчётности) | P2 |
| Лимиты внешних провайдеров (SMS, эквайринг) | Троттлинг при росте нагрузки | Согласование квот заранее, очередь уведомлений с backpressure, деградация до e-mail | P2 |
| Нет версионирования контрактов | Одновременная работа двух контуров ломается | Версии в URL и в заголовках, депрекация по расписанию | P3 |

### 2.5. Персонал и компетенции

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| ИТ-отдел из трёх человек: нет DevOps, DBA, дата-инженера, офицера ИБ | Некому эксплуатировать платформу | Наём: DevOps/SRE, DBA, дата-инженер, DPO, 2–3 backend-разработчика; на старте — привлечение подрядчика | P1 |
| Нет опыта эксплуатации Kubernetes в продуктиве | Ошибки конфигурации, инциденты | Обучение, управляемый Kubernetes, привлечение подрядчика на первые месяцы, runbook | P1 |
| Сопротивление изменениям, теневые Excel-файлы | Данные снова расходятся | Обучение, участие ресепшена и врачей в приёмке, отключение доступа к старым файлам по графику | P2 |
| Нет обучения работе с ПДн | Человеческий фактор как канал утечки | Обязательный курс и проверка знаний, регулярные фишинг-учения | P2 |
| Знания сосредоточены на техническом директоре (bus factor = 1) | Остановка проекта при его отсутствии | Документирование решений (ADR), парная работа, ревью | P3 |

### 2.6. Процессы и организация

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| Нет описанных процессов и SLA | Невозможно проверить эквивалентность старого и нового контура | Описание процессов «как есть» и «как будет», критерии приёмки, метрики SLA | P1 |
| Нет владельцев данных | Некому утверждать классы данных и правила доступа | Назначение владельцев по доменам (медицина, финансы, HR, склад) | P2 |
| Нет регламента cutover и отката, роли не распределены | Хаос в момент переключения | Cutover-план с ролями и точками принятия решения (Task5), репетиция переключения | P2 |
| Совмещение проектной и операционной нагрузки | Срыв сроков, выгорание | Выделение проектной команды, найм на операционные задачи | P2 |
| Закупки не синхронизированы с планом миграции | Оборудование приходит позже, чем нужно | План закупок как часть графика проекта, буфер по срокам | P3 |

### 2.7. Безопасность и комплаенс

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| Перенос ПДн без правовых оснований и уведомления РКН | Предписания, штрафы, приостановка обработки | Уведомление РКН, актуализация согласий, поручения на обработку до начала миграции | P1 |
| Копии продуктива в тестовых средах без обезличивания | Типовой канал утечки | Обезличенные тестовые наборы, запрет копирования продуктива, сканирование сред | P1 |
| Потеря ключей KMS | Данные становятся нечитаемыми (риск доступности) | Резервное копирование ключей в HSM, процедура восстановления, разделение секрета | P2 |
| Расширение поверхности атаки: API, шлюзы, мобильное приложение | Новые векторы атак | Пентест перед выводом в продуктив, WAF, bug bounty на поздних этапах, security review контрактов | P2 |
| Требования 1-го уровня защищённости и сертифицированных СКЗИ | Рост сроков и стоимости | Выбор сертифицированных средств на этапе проектирования, аттестация ИСПДн | P2 |

### 2.8. Наблюдаемость и тестирование

| Причина | Влияние | Мера | Приоритет |
|---|---|---|---|
| Нет нагрузочного тестирования | Узкие места выявятся только в продуктиве | Нагрузочные тесты на профиле ×5 до cutover, тест деградации и восстановления | P1 |
| Нет метрик и трассировки | Невозможно локализовать деградацию между сервисами | OpenTelemetry, VictoriaMetrics, Grafana, дашборды по каждому домену, алерты на SLO | P1 |
| Нет автотестов на права доступа и работу с тегированными данными | Регрессии в безопасности проходят в продуктив | Rego-тесты, интеграционные тесты доступа, проверки тегов в CI | P2 |
| Нет обезличенных тестовых данных нужного объёма | Нельзя проверить поведение при росте ×5 | Генератор синтетических данных на базе обезличенного слоя | P2 |
| Нет учений по восстановлению из копий | Резервные копии могут оказаться нерабочими | Ежеквартальные учения с фиксацией RTO и RPO | P3 |

## 3. Сводные рекомендации по приоритетам

### P1 — до начала миграции (блокирующие)

1. Развернуть отказоустойчивую инфраструктуру и резервную площадку, рассчитать ёмкость с запасом.
2. Перевести 1С в клиент-серверный режим.
3. Закрыть кадровый дефицит: DevOps/SRE, DBA, дата-инженер, DPO, backend-разработчики.
4. Провести инвентаризацию, профилирование и очистку данных, построить мастер-запись пациента.
5. Оформить правовую базу: уведомление РКН, согласия, поручения на обработку.
6. Настроить наблюдаемость (метрики, логи, трассировка) и провести нагрузочное тестирование на профиле ×5.
7. Спроектировать границы сервисов по DDD, чтобы не получить распределённый монолит.
8. Подготовить обезличенные тестовые данные и запретить копирование продуктива в нижние среды.
9. Отработать сценарий переключения ККМ на пилотной кассе с сохранением резервного канала.

### P2 — в ходе подготовки и пилота

Идемпотентность и ретраи, кеширование решений PDP, версионирование контрактов, регламент cutover
и отката с распределением ролей, назначение владельцев данных, обучение персонала, пентест,
согласование квот с внешними провайдерами, промежуточный защищённый файловый обмен с лабораторией,
процедура восстановления ключей KMS, автотесты политик доступа.

### P3 — в течение переходного периода

Оптимизация хранилища под рост объёма, депрекация старых версий контрактов, синхронизация закупок,
снижение bus factor через документирование и ADR, регулярные учения по восстановлению.
