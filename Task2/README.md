## Постановка

Требуется предложить блоки целевой архитектуры, которые обеспечивают соблюдение принципов
Privacy by Design, и отдельный слой для аналитической работы с данными. Диаграмма контекста
показывает систему целиком и её окружение; диаграмма контейнеров показывает, из чего система состоит,
и где именно реализуются privacy-механизмы.

## Ключевое архитектурное решение

**Прямые идентификаторы отделены от предметных данных.** Ни один доменный сервис не хранит ФИО,
телефон и паспорт: он работает с `token_id`, а раскрытие идентичности выполняется отдельным сервисом
(PII Vault) и только при наличии права и цели. Это меняет саму парадигму хранения, о которой говорит
технический директор: утечка прикладной базы перестаёт быть утечкой персональных данных, а выполнение
права на удаление сводится к уничтожению ключа и токена.

Второе решение того же уровня — **политики доступа как код**: правило «врач видит только своих пациентов»
не реализуется в каждом сервисе заново, а описывается один раз в PDP и применяется на каждом вызове.

## Новые блоки архитектуры и их вклад в Privacy by Design

| Блок | Назначение | Принцип PbD | Какие проблемы AS-IS закрывает |
|---|---|---|---|
| **API Gateway + WAF** | Единая точка входа: TLS 1.3, mTLS, rate limit, валидация схемы OpenAPI, запрет неописанных полей | Встроенность в архитектуру, End-to-end security | R4.1, R4.6 |
| **IAM (Keycloak)** | OIDC-аутентификация, MFA, SSO, управление жизненным циклом учётных записей, отказ от общих УЗ | Явность и подотчётность | R1.7, R3.6 |
| **PDP на OPA** | Авторизация ABAC/RBAC: атрибуты «роль», «филиал», «эпизод лечения», «цель запроса»; break-glass с обоснованием | Privacy by Default, минимальные привилегии | R1.1, R2.2, R3.3 |
| **Consent Service** | Электронное согласие с целью обработки, версионирование, отзыв, срок хранения; проверка на каждом вызове | Согласие и контроль пользователя | R1.4, R2.7 |
| **PII Vault + KMS/HSM** | Токенизация прямых идентификаторов, шифрование полей, управление ключами и их ротация, crypto-shredding | Минимизация данных, Full lifecycle protection | R1.3, R2.1, R2.5 |
| **Data Catalog + Tagging + Lineage** | Классификация данных, владельцы, прослеживаемость происхождения и получателей | Прозрачность (Visibility and Transparency) | R4.5, B7, B8 |
| **Audit Log (WORM) + SIEM/DLP** | Неизменяемый журнал доступа с hash-chain, детект аномалий, контроль выгрузок | Подотчётность, обнаружение инцидентов | R1.2, R2.4, R2.6 |
| **Retention Service** | Сроки хранения по тегу, автоудаление, обработка отзыва согласия | Storage limitation | R1.6, R3.7, R6.6 |
| **Egress Gateway** | Единая точка выхода данных наружу: контракты, псевдонимы вместо ПДн, квоты, подпись запросов, IP allow-list | Data Minimization на границе | R4.1, R4.2, R4.3 |
| **Data Masking Service** | Обезличивание и маскирование на границе контуров: услуга → код, ФИО → маска | Минимизация в финансовом и складском контурах | R3.1, R3.2, R5.1 |
| **Движок классификации данных** | Автоматическое определение класса конфиденциальности до загрузки в хранилище (детально — Task6) | Privacy by Default для неразмеченных источников | B8, R2.8 |
| **Сегментация сети (Zero Trust)** | Приватные подсети, NetworkPolicy, отдельные сегменты медицинского, финансового и HR-контуров | Defense in Depth | A11, R3.8 |

## Аналитический слой с учётом Privacy by Design

Задача бизнеса — построить озеро данных для BI, ML и LLM. Требование конфиденциальности решается
не запретом аналитики, а разделением хранилища на слои с разным режимом доступа:

| Слой | Содержимое | Кто имеет доступ | Механизм защиты |
|---|---|---|---|
| **Слой 0. Raw-Restricted** | Сырые данные как есть, включая нераспознанные поля | Только сервисные учётные записи движка классификации | Шифрование отдельным ключом, сетевая изоляция, ограниченный срок хранения |
| **Слой 1. Cleansed-Pseudonymized** | Очищенные данные, прямые идентификаторы заменены токенами | Доменные сервисы и отдельные роли по цели обработки | Токенизация, шифрование, ABAC, полный аудит |
| **Слой 2. Curated-Anonymized** | Обобщённые квазиидентификаторы (возраст пятилетками, район вместо адреса), k-анонимность ≥ 5 | Аналитики, дата-сайентисты | Обезличивание, контроль риска реидентификации |
| **Слой 3. Marts / Feature Store** | Витрины BI (P&L, ABC-анализ, загрузка врачей), признаки для ML | Бизнес-пользователи, ML-инженеры | Только агрегаты, запрет обратного связывания |
| **Слой 4. Sandbox** | Песочница для гипотез | Аналитики | Только данные слоёв 2–3, отдельный сетевой сегмент |

Дополнительные механизмы аналитического слоя:

- **Классификация до загрузки.** Данные не попадают в слои 2–3, пока движок классификации не определил
  класс каждого поля и не применил политику (см. Task6).
- **Контроль реидентификации.** Для витрин рассчитывается k-анонимность; поля с редкими значениями
  (например, редкий диагноз в маленьком филиале) обобщаются или исключаются.
- **Обучение моделей на обезличенных данных.** ML-платформа не имеет сетевого доступа к PII Vault;
  Feature Store хранит признаки, а не исходные значения.
- **LLM во внутреннем контуре.** RAG-сервис строится на документах без прямых идентификаторов;
  запросы и ответы логируются, запрещён вывод данных за пределы контура.
- **Нижние среды.** Копирование продуктивных данных в dev/stage запрещено; тестовые наборы генерируются
  из обезличенного слоя.

## Как архитектура закрывает НФТ

| НФТ | Решение |
|---|---|
| **Безопасность (конфиденциальность)** | Токенизация, шифрование at rest и in transit, ABAC, WORM-аудит, DLP, сегментация; своевременное удаление — Retention Service; прекращение обработки по запросу — отзыв согласия и crypto-shredding |
| **Масштабируемость** | Stateless-сервисы в Kubernetes с горизонтальным автоскейлингом, шардирование PostgreSQL по филиалам, Kafka как буфер и средство развязки, ClickHouse для аналитики; расчёт на рост объёма данных в 5 раз и рост числа пользователей |
| **Сопровождаемость** | Доменные границы (bounded contexts), контракты OpenAPI с версионированием, политики как код (Rego) в общем репозитории, IaC, единый CI/CD с автоматическими проверками работы с тегированными данными |
| **Конфигурируемость** | Политики доступа, сроки хранения, правила классификации, справочники масок и услуг задаются конфигурацией и справочниками, изменение не требует доработки кода и релиза сервисов |

## Промежуточное состояние (MVP, ~2 месяца)

В объём MVP входят блоки, без которых нельзя безопасно запустить самостоятельную запись пациента:

- Портал пациента и портал ресепшена;
- API Gateway, IAM (Keycloak), PDP (OPA), Consent Service, PII Vault, Audit Log;
- Appointment Service и Notification Service (напоминание за день до приёма, видимое ресепшену);
- PostgreSQL с RLS и шифрованием полей, Kafka, минимальный Data Lake и BI на обезличенных витринах.

Категории данных пациента разнесены по доменам:

| Домен | Данные | Модель доступа |
|---|---|---|
| Identity (PII Vault) | ФИО, дата рождения, телефон, e-mail, паспорт | ABAC: раскрытие только по цели и роли, каждое раскрытие в журнале |
| Scheduling | `token_id`, слот, филиал, код услуги, статус | RBAC: ресепшен своего филиала, врач — свои слоты; пациент — свои записи |
| Clinical (EMR) | Диагнозы, анамнез, назначения, результаты | ABAC: врач с активным эпизодом лечения; пациент — только свои данные |
| Billing | `token_id`, код услуги, сумма, статус оплаты | RBAC: касса и бухгалтерия, без медицинской номенклатуры |
| Consent | Согласия, цели, отзывы | RBAC: DPO и сервисы (только чтение решения) |
| HR | ПДн сотрудников | Отдельная ролевая модель, отдельный сегмент |

## Финальное состояние (~1 год)

Добавляются мобильное приложение и голосовой робот с подтверждением и отменой записи, ЭМК и документы,
платёжный шлюз, API-интеграция с лабораторией, CRM, домены ТМЦ и HR, полноценный аналитический слой
с ML и LLM. Включаются автоматические проверки релизов на работу с тегированными данными,
аудит доступа с поиском нетипичных действий пользователей и алертинг при несанкционированном доступе.
