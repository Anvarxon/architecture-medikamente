## 1. Задача и ключевое ограничение

Компания хочет построить озеро данных на основе накопленных Excel-файлов, сканов, выгрузок 1С
и потоков из новых сервисов, чтобы автоматизировать BI, обучать ML-модели и применять LLM.

Ограничение, определяющее архитектуру: **структуры данных на входе меняются и не размечены**.
В Excel-файле «журнал врача» завтра появится новая колонка, в выгрузке 1С — новое поле, а свободный
текст анамнеза вообще не имеет схемы. При этом среди этих данных есть специальные категории ПДн.

Отсюда главный принцип решения:

> Ни один набор данных не попадает в слои, доступные аналитикам, пока для каждого его поля
> не определён класс конфиденциальности и не применена политика обработки этого класса.
> Данные с неопределённым классом попадают в карантин, а не в хранилище.

Это реализация Privacy by Default для аналитического контура: по умолчанию данные считаются
чувствительными, а не открытыми.

## 2. Устройство движка

Движок состоит из четырёх функциональных групп (детали — на диаграмме C2).

### 2.1. Приём и профилирование

| Контейнер | Технологии | Функция |
|---|---|---|
| Ingest Service | Airflow, NiFi, Spark | Пакетная загрузка из файловых источников, БД (CDC), 1С и партнёрских API; контрольные суммы, дедупликация, идемпотентность по идентификатору партии |
| Landing Zone (Raw-Restricted) | S3 + SSE-KMS | Изолированная зона приёма; доступ только сервисным учётным записям; ограниченный срок хранения |
| Schema Registry + Drift Detector | Avro/JSON Schema | Определение структуры, сравнение с предыдущей версией, обнаружение новых и изменённых полей, версионирование схем |
| Data Profiler | Spark | Статистики по колонке: типы, форматы значений, кардинальность, доля пустых, сэмплирование значений |
| Metadata Store | PostgreSQL | Схемы, профили, версии правил, история решений классификатора |

Обработка дрейфа схемы: если Drift Detector видит новое поле, партия не блокируется целиком — новое
поле помечается как `unknown` и отправляется на классификацию; до получения класса оно доступно только
в слое 0. Это позволяет не останавливать загрузку и одновременно не «протащить» ПДн в открытые слои.

### 2.2. Классификация

| Контейнер | Как работает | Что распознаёт |
|---|---|---|
| Rule Classifier | Регулярные выражения, словари, контрольные суммы (валидация СНИЛС и ИНН по контрольному числу), справочники МКБ-10 | Структурированные идентификаторы: СНИЛС, ИНН, паспорт, полис ОМС, телефон, e-mail, номер карты, коды диагнозов |
| ML/NLP Classifier | NER-модель для русского языка, эмбеддинги, классификация по имени колонки и по содержимому | Свободный текст: имена, адреса, диагнозы и жалобы в поле «примечание», нестандартные названия колонок |
| Context Classifier | Графовые правила по связям между полями | Случаи, когда поле безопасно по отдельности, но опасно в связке: дата рождения + пол + район + дата приёма дают реидентификацию |
| Scoring & Decision | Взвешенное голосование классификаторов | Итоговый класс и уверенность; сравнение с порогом автоприменения |
| Steward Review UI | Веб-интерфейс для владельца данных | Разбор случаев ниже порога уверенности; решение стюарда становится обучающей меткой |

Пороговая логика: при уверенности ≥ 0,95 класс применяется автоматически; от 0,7 до 0,95 — данные
загружаются по «пессимистичному» классу (как более чувствительные) и ставятся в очередь на разбор;
ниже 0,7 — карантин. Пессимистичное правило важно: ошибка в сторону избыточной защиты обратима,
ошибка в сторону открытости — нет.

### 2.3. Применение политик

| Контейнер | Функция |
|---|---|
| Policy Engine (OPA) | Правило «класс → действие»: маскировать, токенизировать, обобщить, не загружать. Политики хранятся как код и версионируются |
| Masking & Tokenization | Выполнение действия: хеширование, токен из PII Vault, обобщение квазиидентификаторов (возраст → пятилетний интервал, адрес → район) |
| Quarantine | Отдельный бакет с собственным ключом KMS для наборов с неопределённым или запрещённым к загрузке классом; доступ только DPO |
| Loader | Запись в целевой слой хранилища, простановка тегов и записей lineage |
| Quality & Metrics | Проверки качества (Great Expectations) и сбор метрик классификации |

### 2.4. Governance

Data Catalog (справочник классов и владельцев), Data Lineage (происхождение поля, получатели,
срок хранения), Audit Log в WORM-хранилище, мониторинг и алертинг, роль DPO и владельцев данных.

## 3. Организация слоёв хранилища

Разделение по слоям — основная мера, позволяющая одновременно вести аналитику и защищать данные.

| Слой | Содержимое | Прямые идентификаторы | Кто имеет доступ | Дополнительные меры |
|---|---|---|---|---|
| **Слой 0. Raw-Restricted** | Сырые партии как есть, включая нераспознанные поля | Есть | Только сервисные учётные записи движка | Отдельный ключ шифрования, сетевая изоляция, срок хранения 30–90 дней, полный аудит |
| **Слой 1. Cleansed-Pseudonymized** | Очищенные и типизированные данные, прямые идентификаторы заменены `token_id` | Заменены токенами | Доменные сервисы и отдельные роли по цели обработки | Шифрование полей, ABAC, аудит каждого обращения |
| **Слой 2. Curated-Anonymized** | Витрины с обобщёнными квазиидентификаторами | Нет | Аналитики, дата-сайентисты | k-анонимность ≥ 5, подавление редких значений, запрет джойна по токену |
| **Слой 3. Marts / Feature Store** | Агрегаты BI и признаки для ML | Нет | Бизнес-пользователи, ML-инженеры | Только агрегаты, контроль дифференцирующих запросов |
| **Слой 4. Sandbox** | Песочница для гипотез | Нет | Аналитики | Данные только из слоёв 2–3, отдельный сегмент, срок жизни наборов ограничен |
| **Карантин** | Наборы с неопределённым классом | Возможны | Только DPO | Отдельный ключ, обязательный разбор, запрет автоматической загрузки дальше |

### Меры, дополняющие слои

1. **Тегирование на уровне поля**, а не таблицы: одна и та же таблица может содержать поля разных классов.
2. **Раздельные ключи шифрования по классам** — даёт crypto-shredding: уничтожение ключа делает
   недоступными все данные класса без физического удаления из всех копий.
3. **Запрет обратного связывания**: в слоях 2–4 отсутствует `token_id`, поэтому джойн с
   псевдонимизированным слоем технически невозможен.
4. **Контроль риска реидентификации** при публикации витрины: расчёт k-анонимности и l-разнообразия,
   подавление ячеек с малым числом наблюдений (например, редкий диагноз в маленьком филиале).
5. **Ограничение запросов**: аналитические инструменты работают через тот же PDP, что и прикладные
   сервисы; попытка выгрузить детализацию ниже разрешённой гранулярности блокируется.
6. **Обезличенные нижние среды**: dev и stage получают данные только из слоя 2.
7. **Периодический ретро-скан**: движок регулярно перепроверяет уже загруженные слои — если правила
   обновились и в открытом слое обнаружены ПДн, набор автоматически переводится в карантин
   и создаётся инцидент.

## 4. Метрики эффективности классификации

| Метрика | Определение | Целевое значение | Как помогает оптимизировать систему |
|---|---|---|---|
| **Recall по классу K1 (спец. категория ПДн)** | Доля действительно чувствительных полей, которые классификатор пометил верно | ≥ 0,98 | Основная метрика безопасности: рост пропусков означает, что нужны новые словари, дообучение модели или снижение порога |
| **Precision по классу** | Доля верных срабатываний среди всех срабатываний | ≥ 0,90 | Низкая точность = избыточное маскирование и жалобы аналитиков; сигнал уточнить правила |
| **F1-мера** | Гармоническое среднее точности и полноты | ≥ 0,93 | Интегральная оценка качества по классу |
| **Coverage** | Доля полей с проставленным классом до загрузки в слои 1–3 | 100 % | Любое значение ниже 100 % означает риск незамеченных ПДн |
| **Automation rate** | Доля решений, принятых автоматически без стюарда | ≥ 95 % | Показывает стоимость эксплуатации; падение = рост ручного труда |
| **Доля в карантине** | Объём данных, не прошедших классификацию | ≤ 3 % | Рост указывает на дрейф схем или новый тип источника |
| **Среднее время разбора карантина** | От попадания в карантин до решения стюарда | ≤ 2 рабочих дня | Влияет на актуальность аналитики |
| **Throughput** | ГБ в час и строк в секунду на этапе классификации | Пакетное окно ≤ 4 часов при объёме ×5 | Определяет момент, когда нужно масштабировать кластер |
| **Latency стадий** | Время каждой стадии конвейера | Профилируется по стадиям | Позволяет находить узкое место (обычно ML-классификатор) |
| **Schema drift rate** | Доля загрузок с изменившейся структурой | Отслеживается как тренд | Высокое значение = нужны контракты данных с источниками |
| **Число инцидентов «ПДн в открытом слое»** | Найдено ретро-сканом или аудитом | 0 | Ключевая метрика результата всей системы |
| **Model drift** | Падение качества модели на контрольной выборке | Не более 2 п.п. за квартал | Триггер переобучения |
| **Доля данных с полным lineage** | Поля витрин, для которых прослеживается источник | 100 % | Обеспечивает выполнение запросов субъектов и регулятора |

### Как метрики используются в оптимизации

- Эталонная контрольная выборка (размеченная вручную, обновляемая ежеквартально) — основа
  для измерения Precision/Recall; без неё качество классификации неизмеримо.
- Падение Recall по конкретному типу данных → расширение словарей и правил, дообучение NER-модели
  на новых примерах из Steward Review UI.
- Рост доли ручного разбора → анализ причин: новый источник, дрейф схемы или слишком высокий порог.
- Рост времени обработки → профилирование стадий, увеличение параллелизма, вынесение ML-стадии
  только на неоднозначные поля.
- Все метрики выводятся в Grafana и имеют алерты: например, Recall K1 < 0,98 — это инцидент ИБ,
  а не просто ухудшение качества.

## 5. Масштабируемость

### 5.1. Рост объёма данных

| Механизм | Как работает |
|---|---|
| Горизонтальное масштабирование обработки | Spark-исполнители и воркеры Airflow добавляются под нагрузку; партиционирование по дате и источнику, независимые партиции обрабатываются параллельно |
| Инкрементальная загрузка | CDC вместо полной перегрузки: классифицируются только новые и изменённые данные |
| Кеш решений | Для стабильных схем класс берётся из Metadata Store; повторная классификация запускается только при дрейфе схемы или смене версии правил — это удерживает стоимость при росте объёма |
| Двухуровневая классификация | Дешёвые правила отрабатывают основную массу полей; дорогой ML-классификатор вызывается только для неоднозначных случаев |
| Буферизация | Kafka сглаживает пики загрузки, backpressure защищает от перегрузки |
| Хранилище | Объектное хранилище + ClickHouse/Iceberg: рост объёма решается добавлением ёмкости, а не переархитектурой; горячие и холодные данные разносятся по классам хранения |
| Сэмплирование при профилировании | Классификация ведётся по репрезентативной выборке, а не по всему объёму, при сохранении полной обработки на этапе маскирования |

### 5.2. Рост числа пользователей

| Механизм | Как работает |
|---|---|
| Доступ через PDP | Аналитики и BI обращаются к слоям через тот же механизм авторизации, что и прикладные сервисы; масштабируется репликами PDP с кешем решений |
| Кеширование витрин | BI работает с предрассчитанными агрегатами, а не с детальными данными |
| Разделение нагрузок | Отдельные пулы ресурсов для ETL, ad-hoc-запросов и BI, чтобы тяжёлый запрос аналитика не влиял на регламентные загрузки |
| Квоты и лимиты | Ограничение на объём выгрузки и на сложность запроса, в том числе как мера против массового выкачивания данных |

### 5.3. Расширение функциональности

- **Новые классы данных** добавляются конфигурацией: словарь, регулярное выражение, Rego-политика.
  Изменение кода не требуется — это прямое выполнение НФТ «конфигурируемость».
- **Новые источники** подключаются как коннектор Ingest Service; остальной конвейер не меняется.
- **Новые языки и форматы** (например, распознавание сканов через OCR) добавляются как отдельная
  стадия перед профилированием.
- **Новые требования регулятора** отражаются в политиках и тегах, а затем автоматически применяются
  ко всем данным при следующем ретро-сканировании.
