# Карта защиты данных: что защищаем, чем защищаем, как размечаем

Документ отвечает на три вопроса задания:
1. какие данные защищаем и каким способом (шифрование, обфускация, обезличивание);
2. какими инструментами и мерами обеспечивается конфиденциальность в потоках;
3. как устроен механизм тегирования данных.

---

## 1. Список данных для защиты и способы защиты

Обозначения способов: **Ш** — шифрование, **Т** — токенизация или псевдонимизация, **О** — обезличивание
(анонимизация), **М** — маскирование или обфускация при отображении, **У** — удаление по сроку.

| № | Данные | Класс | Где живут TO-BE | At rest | In transit | In use | Ретеншен |
|---|---|---|---|---|---|---|---|
| 1 | ФИО, дата рождения пациента | K2 | PII Vault | **Ш** AES-256/ГОСТ на уровне поля, ключ в KMS/HSM; **Т** токен вместо значения в прикладных БД | TLS 1.3, mTLS внутри кластера | **М** для ролей без права на раскрытие (`Ив***** И. И.`) | **У** 25 лет после последнего обращения (мед. документация), затем crypto-shredding |
| 2 | Телефон, e-mail пациента | K2 | PII Vault | **Ш** + **Т** | TLS 1.3 | **М** (`+7 (9**) ***-45-67`) | **У** по отзыву согласия |
| 3 | Адрес прописки, место работы или учёбы | K1/K2 | PII Vault, EMR | **Ш** на уровне поля | TLS 1.3 | **М**, в аналитике **О** до региона и отрасли | **У** по сроку договора |
| 4 | Паспортные данные, СНИЛС, полис ОМС | K2 | PII Vault, S3 (сканы) | **Ш** SSE-KMS + шифрование поля | TLS 1.3 | **М** (последние 4 цифры), водяной знак на скане | **У** по истечении срока хранения договора |
| 5 | Диагнозы, анамнез, назначения | K1 | PostgreSQL EMR (по `token_id`) | **Ш** TDE + шифрование поля | mTLS | Доступ по ABAC («свой пациент», эпизод лечения) | **У** 25 лет, затем архив или уничтожение |
| 6 | Результаты лабораторных исследований | K1 | PostgreSQL lab, S3 | **Ш** TDE, SSE-KMS | mTLS, подпись запроса | Доступ по ABAC; наружу — только псевдоним | **У** по сроку мед. документации |
| 7 | Сканы медицинских документов, снимки | K1 | S3 Object Storage | **Ш** SSE-KMS, отдельный ключ на класс данных | TLS 1.3 | Водяной знак с логином, запрет массовой выгрузки (DLP) | **У** по сроку |
| 8 | Хронические заболевания, аллергии из анкеты | K1 | EMR | **Ш** поля | mTLS | ABAC, в аналитике **О** (группировка по МКБ-блокам) | **У** по отзыву согласия |
| 9 | Согласия на обработку и их отзывы | K2 | Consent Service | **Ш** + ЭП | TLS 1.3 | Неизменяемая история версий | Хранится 3 года после отзыва (доказательство) |
| 10 | Наименование медицинской услуги в платеже | K1 | Billing | **О** для финансового контура: код услуги вместо названия | TLS 1.3 | Раскрытие названия — только медицинской роли | **У** по сроку бухгалтерского хранения |
| 11 | Платёжные данные (карта) | K3 | Не хранятся: токен провайдера | **Т** токен PSP | TLS 1.3 | Отображается только маска карты | Хранится токен, не PAN |
| 12 | Договоры с пациентами (PDF) | K2 | S3 | **Ш** SSE-KMS + ЭП | TLS 1.3 | Доступ по роли и по своему договору | **У** 5 лет после окончания |
| 13 | Данные о выручке по пациенту | K3 | Billing, 1С | **Ш** TDE | mTLS | Бухгалтерия видит `token_id` + код услуги | **У** по 402-ФЗ (5 лет) |
| 14 | Зарплатный реестр | K3 | Payroll | **Ш** поля, передача с ЭП | Канал банка, ГОСТ TLS | Доступ только расчётчику | **У** по сроку |
| 15 | ПДн сотрудников: паспорт, СНИЛС, ИНН | K2 | PII Vault, S3 | **Ш** + **Т** | TLS 1.3 | **М** | **У** 50 лет (кадровые документы) или по норме |
| 16 | Медицинские книжки и справки сотрудников | K1 | S3 (домен HR) | **Ш** SSE-KMS, отдельный ключ | TLS 1.3 | Доступ только HR-роли | **У** по сроку трудовых отношений |
| 17 | Цены, условия и контакты поставщиков | K4 | Закупочный сервис | **Ш** TDE | TLS 1.3 | Гриф «коммерческая тайна», доступ по роли | **У** 5 лет |
| 18 | Списание препаратов на кабинет и процедуру | K1 (косв.), K4 | WMS | **Ш** TDE | mTLS | **О** перед аналитикой: препарат → группа, без привязки к пациенту | **У** по сроку |
| 19 | Журналы доступа (кто, что, когда) | K5 | Audit Log (WORM) | **Ш** + hash-chain, защита от изменения | mTLS | Доступ только DPO и аудитору | Хранение не менее 3 лет |
| 20 | Данные в аналитическом контуре (BI, ML) | K0 | Data Lake, витрины | **Ш** на уровне хранилища | TLS 1.3 | **О**: k-анонимность ≥ 5, обобщение возраста и адреса, удаление редких значений | По политике витрины |
| 21 | Тестовые данные в нижних средах | K0 | Dev/Stage | **Ш** | TLS | **О** обязательно: копии продуктива запрещены | Обновление по расписанию |
| 22 | Резервные копии | K1–K4 | Резервное хранилище | **Ш** с отдельным ключом, offsite-копия | Защищённый канал | Доступ только администратору резервного копирования | По политике (например, 30 дней + ежемесячные) |

### Как выбирался способ защиты

- **Шифрование** — для всего, что должно быть восстановимо в исходном виде: медицинские данные,
  сканы, договоры, кадровые документы. Ключи хранятся в KMS/HSM, ротация не реже раза в год,
  отдельные ключи для разных классов данных — это даёт возможность crypto-shredding
  (уничтожение ключа делает данные неустранимо нечитаемыми).
- **Токенизация/псевдонимизация** — для прямых идентификаторов. Прикладные сервисы работают
  с `token_id` и вообще не получают ФИО, если это не требуется по цели обработки. Это резко снижает
  ущерб при компрометации любой прикладной БД.
- **Обезличивание** — для аналитики, ML и нижних сред. Обязательно контролируется риск реидентификации:
  недостаточно убрать ФИО, если остались дата рождения + пол + адрес + дата приёма.
- **Маскирование/обфускация** — для отображения в интерфейсах и отчётах, когда полное значение не нужно
  для выполнения задачи (например, кассиру достаточно последних цифр телефона для подтверждения записи).
- **Удаление** — обязательный элемент: данные, которые больше не нужны, — это чистый риск без выгоды.

## 3. Механизм тегирования данных

### 3.1. Таксономия тегов

Тег — это структурированная метка, привязанная к полю, объекту или набору данных. Используется
многомерная схема: один тег не может одновременно отвечать за конфиденциальность, срок хранения
и правовое основание.

| Измерение | Значения | Назначение |
|---|---|---|
| `confidentiality` | `public`, `internal`, `pii`, `sensitive-pii`, `commercial-secret`, `credentials` | Основной класс конфиденциальности (K0–K5) |
| `pii_type` | `name`, `birthdate`, `phone`, `email`, `address`, `passport`, `snils`, `oms`, `card`, `health`, `bank_account` | Тип персональных данных, определяет способ обработки |
| `legal_basis` | `consent`, `contract`, `legal_obligation`, `vital_interest` | Правовое основание обработки (152-ФЗ ст. 6, 9, 10) |
| `retention` | `p1y`, `p5y`, `p25y`, `p50y`, `until_consent_revoked` | Срок хранения, вход для Retention Service |
| `masking` | `none`, `partial`, `hash`, `tokenize`, `generalize`, `drop` | Действие при попадании в нижние слои и интерфейсы |
| `owner` | идентификатор владельца данных (например, `med_director`, `cfo`, `hr_lead`) | Кто утверждает доступ |
| `residency` | `ru-only` | Ограничение на территорию хранения (ст. 18 ч. 5 152-ФЗ) |

### 3.2. Где тег живёт

Тег проставляется в трёх местах, и все три синхронизируются из Data Catalog как единого источника:

1. **В коде и схемах** — аннотации в OpenAPI и в DDL-комментариях. Пример:

```yaml
# openapi.yaml — фрагмент схемы ответа
components:
  schemas:
    PatientShort:
      type: object
      properties:
        tokenId:
          type: string
          x-data-class: internal
          x-masking: none
        lastName:
          type: string
          x-data-class: pii
          x-pii-type: name
          x-legal-basis: consent
          x-retention: p25y
          x-masking: partial
        diagnosisCode:
          type: string
          x-data-class: sensitive-pii
          x-pii-type: health
          x-legal-basis: consent
          x-masking: generalize
```

```sql
COMMENT ON COLUMN emr.encounter.diagnosis_code IS
  '{"confidentiality":"sensitive-pii","pii_type":"health","legal_basis":"consent",
    "retention":"p25y","masking":"generalize","owner":"med_director","residency":"ru-only"}';
```

2. **В каталоге данных** (DataHub/OpenMetadata) — как glossary terms и tags на уровне колонок,
   с историей изменений, владельцем и связью с lineage.
3. **В объектном хранилище** — как object tags у файлов (`x-amz-tagging`), что позволяет применять
   политики жизненного цикла и разные ключи шифрования по классу данных.

### 3.3. Как тег появляется

| Способ | Когда применяется | Инструмент |
|---|---|---|
| Вручную владельцем данных | Новые доменные сущности при проектировании | Data Catalog, ревью DPO |
| Из аннотаций в коде | Автоматически при сборке сервиса: аннотации выгружаются в каталог | CI-шаг `publish-data-contract` |
| Автоматическая классификация | Неразмеченные источники: Excel, сканы, выгрузки 1С, партнёрские API | Движок классификации (Task6): правила + ML/NER |
| По результатам разбора карантина | Спорные случаи с низкой уверенностью | Steward Review UI, обучающая обратная связь |

### 3.4. Как тег работает

Тег — это не документация, а исполняемая конфигурация. По тегу автоматически принимаются решения:

| Компонент | Что делает по тегу |
|---|---|
| PDP (OPA) | Решает, доступно ли поле роли и цели запроса: `sensitive-pii` требует медицинской роли и активного эпизода лечения |
| PII Vault | Поля с `masking: tokenize` не попадают в прикладную БД в открытом виде |
| Movement-политики хранилища | `confidentiality: sensitive-pii` запрещает загрузку в слои 2–3 без обезличивания |
| Retention Service | Планирует удаление по `retention` и по событию отзыва согласия |
| DLP | Блокирует выгрузку файлов с тегом `sensitive-pii` во внешние каналы |
| Аудит | Обращение к полям `pii` и `sensitive-pii` логируется в WORM-журнал с указанием цели |
| Маскирование в BI | Витрина строится с учётом `masking`: `generalize` → возраст группируется в пятилетки |

### 3.5. Контроль тегирования в CI/CD

Требование финального состояния — «релиз проверяется в автоматическом режиме на работу
с тегированными данными». Реализуется набором проверок в конвейере:

| Проверка | Что делает | Реакция |
|---|---|---|
| `schema-tags-required` | Каждое новое поле в OpenAPI и в DDL должно иметь `x-data-class` | Сборка падает |
| `no-pii-in-logs` | Статический анализ: запрет логирования полей с тегом `pii`/`sensitive-pii` | Сборка падает |
| `contract-diff-review` | Если контракт начинает отдавать поле класса `pii` наружу — требуется ревью DPO | Блокирующее ревью |
| `policy-tests` | Тесты Rego-политик: роль без права не получает `sensitive-pii`, пациент не видит чужие данные | Сборка падает |
| `masking-tests` | Проверка витрин: в слоях 2–3 нет полей с `masking: tokenize`/`drop` | Сборка падает |
| `lineage-completeness` | Каждое поле витрины имеет lineage до источника | Предупреждение, затем блокировка |
| Регулярный скан хранилищ | Периодический поиск неразмеченных данных и ПДн в открытых слоях | Инцидент в SIEM, алерт DPO |

### 3.6. Пример сквозного применения

Поле «результат анализа» приходит из лаборатории:

1. Движок классификации распознаёт структуру ответа и присваивает `confidentiality: sensitive-pii`,
   `pii_type: health`, `retention: p25y`, `masking: generalize`.
2. Тег записывается в Data Catalog, туда же попадает lineage: `лаборатория → Lab Result Service →
   PostgreSQL lab → витрина «загрузка врачей»`.
3. Loader кладёт исходное значение в слой 1 (псевдонимизированный), в слой 2 попадает только
   обобщённая категория результата (норма/отклонение) без `token_id`.
4. PDP разрешает чтение исходного значения врачу, ведущему этот эпизод лечения, и самому пациенту в ЛК;
   бухгалтеру и аналитику — запрещает.
5. Каждое чтение попадает в WORM-журнал; десять и более чтений разных пациентов за минуту
   порождают алерт в SIEM.
6. При отзыве согласия Retention Service уничтожает токен пациента: значения становятся
   несвязываемыми с субъектом, факт удаления фиксируется в журнале.
